## Findings: causes versus hypotheses

### Confirmed from available artifacts

1. **The work product and the benchmark objective diverged.** PR #141 primarily describes the implementation of execution, accounting, scoring, data generation, batching, and recovery infrastructure. The actual results are explicitly called diagnostic, synthetic, non-qualifying, or limited. No PR evidence demonstrates a completed independent benchmark comparison.
2. **The goal had no project-level stop rule or benchmark completion gate.** The original `goal-objective.md` sets an extensive implementation/E2E scope, says to continue after the first problem, and gives no overall time-box, iteration cap, or “benchmark matrix complete” gate. It does set narrower safeguards: no subscription-consuming request before separate approval, no merge, and bounded live-smoke scope. The board’s “# 141 PR live test” note says the expectation was to confirm the cycle worked overall; it then asks why time ran long without completing all benchmarks and specifically says to produce a detailed plan instead of another general goal. This confirms mismatch between broad runtime repair work and the desired benchmark outcome, rather than proving an automated supervisor loop.
3. **The execution objective was broader than the benchmark acceptance target.** The objective asked for full v0.2 runtime implementation, extensive failure-mode coverage, and reproducible E2E evidence; it did not require the complete multi-task benchmark suite. Consequently, successful component work could satisfy local subgoals while leaving the benchmark expectation unmet. The board note retrospectively calls the task too broad and says it focused on small issues; that is consistent with the goal text but remains an owner assessment, not telemetry proving why each decision was made.
4. **Unknown settlement was surfaced, not hidden.** A local PR #141 attempt stopped with unknown usage and zero observed tokens. A successful separate diagnostic is reported later. Cost for the ambiguous attempt remains unknown; it cannot be reported as a confirmed charge or as zero spend.
5. **The PRs do not establish a cost overrun.** They report token observations and caps for some runs, and repeatedly state monetary cost UNKNOWN. No invoice or reconciled provider billing record is present in the reviewed evidence.

### Remaining unknowns

- **Harbor blocker:** #145 confirms a handoff/integration need for one frozen Newton child, but not that Harbor consumed most of the earlier effort or caused the PR #141 scope drift.
- **Supervisor loop:** the recovered logs and PRs do not establish repeated supervisor-selected tasks, automatic retries beyond the separately documented diagnostic attempts, or a specific supervisor defect.
- **Time and total attempts:** session and PR dates show active work on Nov 8–10 and follow-up preparation Nov 13; they do not establish continuous work duration, person-hours, or complete count of attempts.
- **Monetary impact:** unknown-settlement calls remain unreconciled in reviewed evidence; no provider invoice was found.

## Preventive rules for the next campaign

1. **Freeze one benchmark acceptance contract before implementation.** Name the independent task/suite, baseline and treatment arms, sample count, score, evidence requirements, and deadline. No infrastructure item counts as progress toward acceptance unless it removes a named blocker in that contract.
2. **Use stage gates with a fixed investigation budget.** At each gate (local preflight, one bounded live smoke, benchmark matrix), record spend/call/time ceilings and a stop condition. If a gate fails, allow one documented diagnosis/fix cycle, then return to the benchmark or explicitly replan.
3. **Treat unknown settlement as a hard stop.** Preserve the attempt ledger, reconcile it before any retry, and require a new explicit bounded authorization for a new run. Never report unknown usage as zero cost.
4. **Keep diagnostics separate from benchmark claims.** Label synthetic, fixture-backed, tiny-split, and offline results as diagnostics in the report; benchmark completion requires the predeclared independent suite and baseline comparison.
5. **Require an operator-ready handoff for external evaluators.** Before opening a Harbor integration task, verify the pinned image, public evaluator contract, approved child, and dry-run path. Assign an owner and deadline; if the handoff is blocked, record that blocker without turning it into an unbounded framework-building branch.
