# Песочница BananLoop: банковский маркетинг

Небольшой проект классификации на CPU на основе набора данных UCI Bank
Marketing. Нужно оценить вероятность того, что клиент оформит срочный вклад,
используя сведения, доступные **до** текущего телефонного звонка.

Это более содержательная задача для BananLoop, чем маленький учебный набор:
здесь 41 188 записей, числовые и категориальные признаки, редкий положительный
класс, временной сдвиг и признак, который нельзя использовать, потому что он
становится известен только после звонка.

Источник: [UCI Bank Marketing](https://archive.ics.uci.edu/dataset/222/bank%2Bmarketing),
Moro, Rita и Cortez (2014), DOI
[10.24432/C5K306](https://doi.org/10.24432/C5K306), лицензия CC BY 4.0.
Расширенная версия `bank-additional-full.csv` отсортирована по времени. В
подготовленных файлах порядок сохранён, а данные разделены на непрерывные
временные отрезки: 70% — обучение, затем по 10% — для dev, validation и
финального holdout. Состав разбиений описан в `data/metadata.json`.

## Задача

Предсказывать значение `y` по остальным доступным полям. Признак `duration`
удалён из всех разбиений: это длительность текущего звонка, поэтому до звонка
она неизвестна. Validation и финальный holdout находятся в `.bananloop_eval/`;
BananLoop должен зафиксировать эти файлы и скрыть их от исполнителей
экспериментов. Не копируй записи и метки из этой папки в `data/`.

Базовая модель — конвейер scikit-learn с логистической регрессией,
one-hot-кодированием категориальных признаков и масштабированием числовых.
Она намеренно простая, чтобы эксперименты заметно отличались от базового
результата и не требовали GPU. Данные помещаются в память; оценивание должно
работать только на CPU и использовать не более двух потоков.

## Запуск в Codex

Открой эту папку как проект Codex и попроси:

> Используй `$bananloop-goal`, чтобы улучшить `pr_auc` на хронологическом бенчмарке Bank Marketing. Не допускай ухудшения на validation, не подбирай модель по финальному holdout и не используй `duration` или другие сведения, появляющиеся после звонка. Работай только на CPU, максимум в два потока; оценивание каждого кандидата должно занимать меньше 60 секунд. Если бюджета хватит, проверь несколько разных гипотез: регуляризацию или веса классов, временные и категориальные признаки, ограниченную нелинейную модель. Порог классификации и калибровку рассматривай как дополнительные диагностические показатели. Для доступных разбиений приведи PR-AUC и balanced accuracy, объясни временной сдвиг, укажи затраты и итоговую лучшую модель. Не изменяй оценщик, зафиксированные разбиения, метки и условия этого бенчмарка.

Обычный сценарий `$bananloop-goal` изучает проект и запускает кампанию с
лимитом до четырёх экспериментов. Этого достаточно для базовой модели и
нескольких заметно различающихся подходов без параллельного обучения.
Финальный holdout предназначен только для оценки итогового кандидата.

Оценщик возвращает одну и ту же основную метрику `pr_auc` для dev, validation
и holdout. Это позволяет BananLoop сравнивать разбиения без отдельных названий
метрик вроде `validation_pr_auc`. Balanced accuracy и доля положительного класса
выводятся как дополнительные показатели, а не заменяют PR-AUC.

## Команды оценщика

Эти команды BananLoop должен использовать для существующего оценщика:

```bash
python .bananloop_eval/evaluate.py --split dev
python .bananloop_eval/evaluate.py --split validation
python .bananloop_eval/evaluate.py --split holdout
```

Dev и validation используются при оценке кандидатов. Holdout следует запускать
только для итоговой модели. Этот бенчмарк нужен для демонстрации процесса
экспериментов, а не для выводов о поведении реальных клиентов или готовности
модели к внедрению.
